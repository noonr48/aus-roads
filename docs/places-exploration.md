# Offline places exploration (v1.2)

The existing four-tab app keeps Map, Explore (`nearby` route identity), Pins and Settings. Explore has two always-visible modes: Discover for leisure places and Essentials for fuel, emergency and travel services. Essentials retains its own model; emergency information comes before coordinate details. Distances refer to the current map area, not an invented GPS fix, and are straight-line distances rather than drive times.

## What the app knows

A fresh install carries a standard SQLite, FTS-free South Australia catalog derived from the existing real OSM pack. The bundled asset has 129,957 indexed features, including 19,085 POIs and 1,189 parks. `catalog/sa-search.json` records the component/source SHA-256 values, row and class counts, OSM source/extract timestamp and ODbL attribution. The extractor's source is the September 2026 SA pack; this is not live venue information.

Search understands place-name words and explicit category keywords such as coffee/café, parks/walking, museums/art, viewpoints, picnics, play/sport and camping. Supported categories map to actual full OSM tags, not invented tags or descriptions. Unrecognized words remain literal name filters. SQL values are bound, including literal percent/underscore/backslash characters. Candidate acquisition has a separate quota per category so dense cafés cannot remove sparse parks before ranking; actual great-circle radius filtering happens before display.

Opening hours, prices, venue quality, accessibility, dog friendliness and current conditions are **not** known or inferred. No accounts, cloud recommender, telemetry or new permissions are added. The offline flavor still has no INTERNET/location permissions; the network flavor preserves its existing capabilities.

## Interests and visits

Interests, the new-places preference and explicit visits live in local DataStore. Only **Mark visited**, **Undo** or a confirmed history-clear action changes visits. Searches, map selections, saved pins, started routes and GPS fixes never become inferred visits.

Suggestions have deterministic, truthful reasons: the current keyword, an explicit interest, affinity from explicitly marked categories, a new nearby stop, or a previously marked place. Visit association uses normalized name/kind/tag and approximately one-metre coordinates because legacy catalogs contain generated row IDs, not stable OSM identity. It survives row order/ID changes; a moved or renamed place may require a new explicit visit. The association format remains v1 and is cached only on owned immutable search-result objects.

Persistence failure is not optimistic success. Read failures do not reset interests/history; write failure retains the exact requested mutations by concern for Retry. Undo submitted while another save is suspended is drained after that save rather than discarded. A successful Undo cannot erase an unrelated failed preference change; explicit Retry applies retained intents in order, and confirmed history clear supersedes pending/failed visit edits without changing interests. If malformed visit metadata prevents reading, the interests sheet still offers a separately confirmed **Clear visit history** action: it clears only visits, preserves interests/pins/routes, and restarts the preferences read. Ordinary preference edits remain disabled until a successful read. Visit notices are consumed on completion/cancellation and invalidated after clearing history, so an old Undo cannot replay after returning to a screen.

## App joins and recovery

- Adopted `current.json` plus contained relative component paths is authority. Newer orphan directories never become an installed index or map.
- Catalog bootstrap copies/checks the public bundled asset atomically, verifies its SHA and schema/integrity, and reports unavailable/corrupt state separately from zero matches.
- Index reads/open/close serialize; generation changes refresh unchanged map/essential searches and superseded results cannot publish. Essentials withdraws old emergency/category data as soon as catalog loading begins, cancels both in-flight jobs, and rejects completion unless token, reference, generation and READY still match. Initial loading is not a failed lookup; terminal unavailable/failed state is explicit, and the same selected category reloads when a ready epoch returns. Map text queries carry an edit serial: A→B→A inside a debounce window (including same-turn conflation) reruns the returned A rather than leaving empty/spinning results; identical query events preserve completed results. Cameras observe catalog readiness and generation at the last viewport, so startup and replacement do not require a pan. An absent optional camera table remains supported for old packs, but schema/query faults from a present table propagate into the fixed CAMERAS_QUERY health seam; canceled or superseded layers cannot publish.
- Map search results show an approximate straight-line distance from the shared map area, not GPS or a drive-time estimate. This disambiguates same-named segments without changing matching/order; absent reference or invalid catalog coordinates omit the cue. While its nonblank text-search UI is foregrounded, only secondary camera drawing/hits/sheets are suspended. Clear/selection restores individual camera IDs and taps; active navigation overrides suppression, and disabled camera settings are never overridden. Camera viewport queries/alerts/data remain unchanged.
- A failed Map text search exposes **Retry search**, which repeats the exact query with a fresh request serial, without changing text or catalog generation. Its feature-level `SearchHealth` contract joins the app's persistent `MAP_SEARCH_QUERY` outcome witness; blank/canceled/superseded queries do not claim success or failure.
- Map asset preparation, hashing and SQLite validation run on I/O. A composition-owned transaction withdraws and replays native overlays/listeners around main-thread style replacement while retaining the MapView, camera, discovery selection, editor state and domain/service owners. Derived bundled caches use validated atomic replacement; a failed copy or native style load has an explicit error/Retry and persistent MAP_ASSETS/MAP_STYLE witness. Canceled preparation/callback publication is guarded; a held callback test proves the helper API boundary, not delayed JNI timing.
- A place's **On map** action uses an internal, one-shot selection, shows a zoom-independent destination marker/details and does not calculate a route. Selection requested while map assets are unavailable remains pending through Retry and is consumed only after a ready map. **Directions** is a separate explicit action.
- The navigation graph has a stable Map root; NavController owns back-stack restoration. Back dismisses details then returns to the existing discovery state.
- Private `no_backup/places-health.json` stores fixed-cardinality seam metadata only. No entered queries, venue names, coordinates or preferences are logged. Health read/write/fsync work runs on a bounded serialized I/O worker, not the UI thread. Oversized/corrupt diagnostic state produces a read alarm and reset counter; log limits apply per fixed seam, so a noisy catalog cannot hide a first preferences failure.
- Offline/no-account wording is visible before discovery results; Settings explains the distinction between statewide place listings and the included Adelaide map demo. This is not a promise of live venue data or statewide bundled map tiles.

## Rebuild the public asset

From the repository root, with the existing hash-matching pack artifacts:

```sh
python3 tools/map-pack-builder/scripts/bundle-search-catalog.py \
  --source tools/map-pack-builder/dist/search.db \
  --manifest tools/map-pack-builder/dist/manifest.json \
  --out android/app/src/main/assets/catalog
python3 -m unittest discover -s tools/map-pack-builder/tests -p test_bundle_search_catalog.py
```

The builder refuses source-hash, coverage, license or coordinate failures before publishing a candidate; it preserves optional road-speed/camera tables and emits no virtual FTS tables.
